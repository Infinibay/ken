# Revisión del IR contra errores del corpus

Estado: revisión del IR 1.17.0 y propuesta de implementación. Las relaciones
propuestas aquí no están disponibles por el hecho de aparecer en este documento.

Actualización de implementación: IR 1.19.0 corrige el caso secuencial de valores
sobrescritos en Python, JavaScript, TypeScript, Java y C#. Publica `RETURN_ORIGIN`,
`RETURN_REACHES` y estado por callable para ese pase. Ramas, bucles y los demás
casos no soportados conservan las limitaciones del resumen anterior. Ver la
[auditoría del cambio](../../structural-validation/multilanguage/return-flow.md).

## Conclusión

Conservar el grafo de propiedades y KenQL. Extender el modelo semántico y sus
pases: el problema principal no es la sintaxis de búsqueda ni Python frente a
Rust. El diseño original ya prevé buena parte de estas capacidades, pero el
prototipo no las implementa con suficiente precisión.

## Hallazgo reproducido: asignaciones sin versión

En Python, Java y TypeScript, el programa equivalente a:

```python
class Product: pass
def build():
    x = Product()
    x = None
    return x
```

produce `build RETURNS_NEW Product` sin atributo de incertidumbre. La reproducción
no tiene diagnósticos de parsing. `semantic.py` recorre todas las `ASSIGNED_FROM`
de un almacenamiento al resolver `RETURNS`; no distingue qué definición alcanza
ese retorno. La construcción existe, pero su resultado fue reemplazado.
El [probe ejecutable](../../../examples/bench/probe_ir_assignment_precision.py)
registra fuentes, hashes del motor, expectativas y hechos observados.

No usar `RETURNS_NEW` como garantía de valor retornado hasta corregir ese contrato.
Tampoco basta con cambiar el nombre de la relación: las queries que consumen
estos resúmenes deben declarar qué grado de evidencia aceptan.

## Cambios necesarios, por prioridad

| Prioridad | Extensión | Caso que la exige | Criterio de aceptación |
|---|---|---|---|
| P0 | Ocurrencias de escritura y lectura, valores por definición, definiciones alcanzables | Retorno después de sobrescribir; variantes de Builder/Prototype | El ejemplo anterior no tiene un retorno nuevo cierto; ramas y bucles conservan alternativas sin elegir la conveniente |
| P0 | Cobertura por ámbito y relación; procedencia y modalidad de hechos derivados | Diferenciar no-match, desconocido y query completa | Terminar la enumeración no certifica completitud semántica; límites de propagación y targets externos quedan explícitos |
| P1 | Accesos con base, miembro declarado y ocurrencia separados | Copia campo a campo de Requests; campo heredado de Flask | `a.x` y `b.x` comparten declaración cuando corresponde, pero no identidad de almacenamiento sin prueba de alias |
| P1 | Resúmenes de flujo por sitio de llamada y efectos de la acción | Falso Command de copia o búsqueda de plantilla; handler adaptado de Flask | Un resultado transmitido o adaptado no equivale a ejecutar la acción; argumentos de llamadas distintas no se mezclan |
| P1 | Procedencia de elementos de colecciones y snapshots | Observer de RxJS con Set → Array.from → alias → bucle | Relacionar elementos de la instantánea con el registro sin afirmar identidad entre ambas colecciones; otro registro no satisface la query |
| P2 | CFG, salidas excepcionales, suspensión y regiones de ejecución | Retry de Tenacity, cache-aside con retorno temprano, recursos y threads | Distinguir orden fuente de ejecución, cleanup que reemplaza retornos y ejecución diferida de closures/generadores |

### Contrato de valores y accesos

Introducir primero ocurrencias neutras ligadas a operaciones: escritura → lugar,
escritura → valor, lectura → lugar y lectura → definiciones alcanzables. Un lugar
puede ser un local, un miembro con una base o un elemento indexado. Los valores
de una asignación no son el mismo nodo que el almacenamiento mutable.

El análisis inicial puede cubrir bloques rectos con resolución exacta. Para ramas,
loops o llamadas con efectos desconocidos, conservar alternativas `may` y cobertura
parcial; no emitir una certeza por haber visto una asignación en algún lugar.
SSA completa no es requisito para representar este contrato. Sí lo es para una
implementación que decida usar SSA internamente y quiera demostrar sus garantías.

Las relaciones agregadas existentes pueden mantenerse como vistas estructurales
documentadas. Una vista de retornos precisos debe depender de las lecturas y sus
definiciones alcanzables, con evidencia del pase y sus límites. Cambiar la semántica
de una vista pública exige migración, versión de IR e invalidación de cachés.

### Resolución y modelos de biblioteca

Flask necesita resolución de miembros heredados y métodos efectivos, preservando
overrides, shadowing y ambigüedad. No se arregla unificando todos los campos con
el mismo nombre. Su clave de despacho viene de un acceso a miembros, no de un
parámetro directo: la query también necesita una variante para ese uso.

RxJS necesita un modelo de copia de elementos y ejecución de callbacks. Reconocer
`Array.from` requiere comprobar la identidad de la API y excluir un `Array` local.
Un snapshot puede conservar referencias a elementos y, a la vez, tener membresía
independiente después de `clear`. No agregar una arista genérica de alias entre
snapshot y colección original. Los modelos de biblioteca deben estar versionados
y separados del lowerer neutro.

### Yield, callbacks y concurrencia

El IR ya preserva operaciones `YIELD`/`AWAIT`, ownership de closures y ciertos
efectos de APIs de concurrencia. Eso no demuestra cuándo se ejecuta un cuerpo.
Crear un generador y consumirlo son eventos distintos; yield-from/yield* tienen
delegación y valor terminal además de elementos producidos. Registrar un callback
no prueba que el receptor lo invoque. Crear un contexto tampoco prueba que se
espere su finalización. Expandir estos modelos por lenguaje con evidencia de API,
cancelación y escapes antes de escribir reglas que afirmen ausencia de bugs.

## Qué no se resuelve ampliando el IR solamente

Command, Strategy y un delegado pueden compartir estructura e incluso efectos.
Conservar interpretaciones y sus evidencias; no excluir una por nombres como
`copy` o `execute`. Requests requiere además una variante de Prototype con copia
de campos posteriores a la creación. Commons IO y el Originator C++ requieren
mejorar las condiciones del catálogo y revisar intención. Un CFG más rico no
convierte automáticamente esas intenciones en propiedades decidibles.

## Validación y coste

Cada pase necesita positivos, negativos y mutaciones en varios lenguajes: reasignar
antes/después de leer, ramas incompatibles, shadowing, bases diferentes, callbacks
no ejecutados y registros distintos. Acompañar cada corrección con la reproducción
OSS fijada a commit y hash; medir cambios en coincidencias y pruebas, no solo counts.

Materializar análisis costosos bajo demanda, por callable y por familia de
relaciones. Cachear resúmenes con versión del pase, dependencias y configuración;
invalidar consumidores cuando cambia un resumen. Evitar clausuras transitivas
globales de alias y CFG. Medir construcción del grafo, consulta, caché fría/caliente
y memoria máxima por separado antes de decidir un backend Rust.
