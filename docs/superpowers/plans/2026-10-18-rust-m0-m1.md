# Ken Rust M0/M1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fijar una referencia Python reproducible y entregar `ken-rs status [PATH] [--json]` nativo, compatible y sin alterar los originales.

**Architecture:** Una referencia congelada y fixtures independientes alimentan un comparador de procesos. `ken-core` posee proyectos, lectura de estado y health local; `ken-cli` posee argumentos y presentación. Se añaden capacidades funcionales por tarea; no hay crates vacíos, comandos delegados a Python ni cambios de formato persistente.

**Tech Stack:** Rust 1.95.0, edition 2024, Cargo resolver 3; clap 4.5.60; rusqlite 0.40.2 con SQLite bundled; serde 1.0.229 / serde_json 1.0.154; ureq 3.4.2; soft-canonicalize 0.5.6; uzers 0.12.2 en Unix; thiserror 2.0.21; tempfile 3.27.0 para tests. Python 3.12.9/pytest y SDK MCP instalados son tooling de referencia.

**Spec:** [Contrato general aprobado](../specs/2026-10-18-rust-migration-design.md) y [M1 aprobado](../specs/2026-10-18-rust-foundation-status-design.md). Leer ambos antes de ejecutar.

Estado del plan: escrito y autorrevisado; pendiente de revisión del usuario y elección del método de ejecución. **Ninguna tarea de implementación está iniciada.**

## Global Constraints

- Rama `codex/rust-migration`; conservar los cambios previos sin reset, stash ni commits ajenos. Continuar en este checkout: contiene la referencia sin commitear; un worktree desde HEAD no la reproduce.
- «No se elimina, renombra ni vacía ningún archivo original durante M0–M7». M0/M1 no modifica código, tests, configuración ni recursos originales; sólo añade archivos propios. Las especificaciones sólo cambian para registrar decisiones/revisiones.
- El ejecutable temporal es `ken-rs`; no sustituir `ken`, reinstalar hooks ni cambiar configuraciones de clientes del usuario.
- «PATH vale `.` por defecto»; `KEN_PROJECT_ROOT` no vacío prevalece; override inválido no activa búsqueda alternativa.
- «Se conservan los quince contadores de `StatusCounts`»; muestra de paths faltantes: «los cinco primeros en el orden vigente».
- Health: `http://127.0.0.1:PORT/health`, bearer local y «timeout vigente de 1 segundo»; sin spawn ni envío de código.
- Ausencia de proyecto: exit 1. Errores de argumentos: exit 2. Proyecto válido, incluso sin DB: exit 0. Datos corruptos/incompatibles: fallo explícito, nunca informe exitoso.
- «M1 no aplica migraciones ni escribe en bases del usuario». No usar `immutable=1` para una base activa con WAL; no cambiar pragmas persistentes ni hacer checkpoints.
- «El mínimo de plataformas a conservar es el de CI actual, Linux y macOS». M0 audita por separado cualquier soporte Windows prometido; no lo certifica por inferencia.
- CPU obligatoria. Informar arranque, respuesta completa y RSS sin añadir un SLA de `status`. Los umbrales de búsqueda/KQL del contrato general siguen vigentes para sus etapas; M1 no los certifica.
- No supresiones, stubs, tests omitidos ni aserciones debilitadas para obtener verde. Una dependencia que no compile en el toolchain fijado exige corregir y registrar el plan antes de continuar.

## Review Focus

1. Symlink seguido de `..` o destino inexistente: resolver primero su semántica real y rechazar escapes; no confundir normalización léxica con confinamiento. Tests: T4.
2. Entorno heredado del usuario: override, HOME, configuración, proxy y cwd no deben consultar el proyecto real ni enviar el bearer a un proxy. Tests: T1/T3/T6/T8.
3. WAL activo y datos que cambian entre lecturas: observar commits publicados en un snapshot de lectura, sin ignorar WAL ni mutar datos. Tests: T5/T8.
4. Health vacío, inválido, lento o redirigido: conservar la degradación a detenido y la evaluación diferida de credenciales; nunca arrancar un proceso. Tests: T6/T7.
5. Formatos limítrofes: redondeo half-even, 15 contadores, orden de recomendaciones y omisión de inventarios sólo en texto. Tests: T5/T7/T8.

## Decisiones fijadas para ejecutar

**Ubicación y dependencias.** Workspace virtual con miembros explícitos, `publish=false`, versión Rust compartida `0.18.0` y un único `Cargo.lock`. T8 compara `--version` con Python para detectar deriva; no se crea release ni tag. Fijar las dependencias directas con `=VERSION`; defaults de ureq deshabilitados (HTTP local sin TLS/gzip), rusqlite sin defaults y con `bundled`, serde con `derive`, clap con `derive`. `uzers` es dependencia Unix. Toolchain `1.95.0`, perfil minimal más rustfmt/clippy; el lock también fija transitivas. T4/T5 verifican compilación real y features; este plan no afirma haberlas compilado.

**Responsabilidades.** `ProjectLocator` y `StatusReader` se representan mediante funciones; `ProjectPaths` y los informes son datos. Sólo health necesita un trait: permite usar el mismo lector con transporte real y un probe determinista en tests. No añadir una abstracción genérica de repositorio ni un runtime async para este comando.

**Expansión de paths según el caller actual.** Python aplica `expanduser()` al override `KEN_PROJECT_ROOT` y a los paths de `resolve_project_path`; no al PATH literal que `status` recibe por argv. Un `~` sin comillas puede haber sido expandido por el shell antes de invocar cualquiera de los binarios. T3/T4 distinguen estos casos: no introducir una expansión automática de un PATH entrecomillado durante la reescritura.

**Referencia.** El manifiesto inicial identifica 1.066 archivos, pero no puede reconstruir el contenido. T1 crea una copia local de esos archivos, más los archivos no ignorados necesarios para ejecutar los comandos y tests de referencia. El manifiesto ampliado describe exactamente qué se incluyó. No copiar `.git`, `.venv`, `.ken`, credenciales ni cachés privadas; no commitear la copia ni cambios del usuario. La suite completa de Python se mide en el checkout con hashes verificados; la copia aislada es el oráculo de CLI/MCP y fixtures M1. El intérprete/paquetes se identifican aparte; `ken.__file__` debe apuntar a la copia durante los ensayos diferenciales.

**Dónde se ejecutan los tests.** `tests/rust_migration/` prueba tooling Python y forma parte del pytest existente, sin requerir Cargo. `migration_tests/` prueba el binario ya construido y se invoca explícitamente en el nuevo workflow y en el cierre local. Esta separación evita introducir una dependencia Rust en la CI Python actual; ninguna prueba se marca skip por no encontrar un binario. Si falta, la suite de paridad falla con diagnóstico.

**Comparación.** JSON se compara por claves/tipos/valores, conservando orden de arrays. Sólo se normalizan el campo `project_root`, `db.path` y las posiciones conocidas de rutas temporales en texto/error. No se borran campos, ordenan recomendaciones, redondean números extra ni eliminan errores. Los puertos y tiempos de health se controlan con servidores de fixture; no necesitan enmascararse en el informe. Los dos motores reciben copias independientes de una misma fixture, con identidad y token sintéticos fijos.

**Diferencias deliberadas ya cubiertas por la especificación.** No reproducir tracebacks Python para datos corruptos: exit 1, stderr con prefijo `ken-rs status:`, sin stdout exitoso ni credenciales. No seguir ningún redirect de health ni proxies heredados: un 3xx produce detenido. El timeout global de health incluye leer el body. La lectura Rust no reproduce los efectos de los pragmas Python. Las diferencias concretas se fijan por case ID en `m1-cases.json`; no existe un bypass genérico de «ambos fallaron». Una divergencia nueva bloquea su tarea hasta revisar el contrato.

## Contratos de datos compartidos

- Tooling Python usa `Path` y objetos JSON. `Reference` contiene `root`, `manifest_path`, `fingerprint` y `python` (path del intérprete). `Case` contiene `id`, `scenario`, `mode` (`json|text|error`), `argv`, `expected_exit`, `expected`, `exception_id` opcional. `ProcessResult` contiene `argv`, `returncode`, `stdout`, `stderr`, `duration_ns`.
- `Fixture` contiene `root`, `expected_report`, `before_state` y `health_log`; ofrece `close()` y context manager. No contiene el proceso del motor. Los casos WAL mantienen abierta su conexión escritora hasta finalizar el ensayo.
- Rust `DiscoveryContext { cwd: PathBuf, forced_root: Option<OsString>, home: Option<PathBuf> }`; se captura una vez en CLI y se pasa explícitamente. No mutar entorno global en tests Rust concurrentes.
- `ProjectPaths` guarda la raíz absoluta resuelta; expone `root()`, `meta()`, `db()`, `port()`, `pid()`, `log()` y `resolve_inside(&Path, &DiscoveryContext) -> Result<PathBuf, ProjectError>`.
- `StatusReport` es un enum: `MissingProject { error: String }`, `MetadataOnly(ProjectStatus)`, `Installed(InstalledStatus)`. `ProjectStatus` contiene raíz, `project_id: serde_json::Value` y `DatabaseStatus { path, exists, size }`. Así no se acepta una combinación imposible de campos opcionales como informe exitoso.
- `InstalledStatus` añade `counts: StatusCounts`, `index_health: IndexHealth`, `rank_signals: RankSignals`, `embedding_coverage: EmbeddingCoverage`, `recommendations: Vec<String>`, `daemon: serde_json::Map<String, Value>`.
- `StatusCounts` tiene quince campos `u64`: `files`, `files_embedded`, `symbols`, `symbols_embedded`, `sessions`, `active_sessions`, `contexts`, `prompt_contexts`, `prompt_contexts_embedded`, `interactions`, `session_scores`, `findings`, `findings_embedded`, `intent_sources`, `intent_sources_embedded`. `IndexHealth { stale_files: u64, sample: Vec<String> }`; `RankSignals { index, embeddings, predictive, findings: String }`; `EmbeddingCoverage { embedded: u64, total: u64, percent: f64 }`.
- `StatusError` distingue proyecto/rutas, metadatos inválidos/campo ausente, SQLite y lectura de archivos. Mantiene causa y path; nunca incluye el token ni el body de health. `ProjectError::EscapesRoot` presenta `path escapes project root:`. Ningún error de datos utiliza `panic!`.
