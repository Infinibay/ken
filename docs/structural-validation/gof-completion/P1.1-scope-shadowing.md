# P1.1 — Ámbitos y shadowing block-scoped (PARCIAL)

Estado: **parcial — rechazo conservador implementado; resolución léxica completa
pendiente en el frontend**.
Fecha: 2026-09-13. Base: `1ee12c1` (post manifiesto de xfail).

## Problema reproducido

El frontend indexa un binding local por `(owner, nombre)`
(`Frontend.storage` → `self.names[(scope, name)]`), así que **dos declaraciones
con el mismo spelling en bloques léxicos distintos de un mismo callable
colapsan en un único `STORAGE`**. El pase `structured-locals/3` recorría las
ramas y unía las escrituras de ambos bindings como si fueran uno solo, emitiendo
un origen que **no es alcanzable** en el punto de lectura.

Java, dentro de una región (`if`), que es lo que hace que el pase no lo rechace:

```java
class A {
  static int make(int n){ return n; }
  static int take(int n){ return n; }
  static int run(boolean flag){
    int x = make(1);
    if (flag) { int x = 0; take(x); }
    return take(x);
  }
}
```

Observado antes del cambio (idéntico en javascript, typescript y csharp):

```text
status: supported
ARGUMENT_ORIGIN CALL:188@188:195  operand=STORAGE:x
  modality=may  origins=[CALL:130@130:137, VALUE:163]
```

`CALL:130` es `make(1)` y `VALUE:163` es el literal `0` **del `x` sombreado**.
En `return take(x)` el `x` interno ya está fuera de alcance: el único origen
posible es `make(1)`. El pase fabricaba una unión imposible (`VALUE:163`).

Por qué `if` y no un bloque desnudo: un bloque `{ ... }` no es región y el pase
ya lo rechazaba con `nonlocal-or-nested-write`. El brazo de un `if` **sí** es
región, así que el write sombreado entraba en el merge de brazos.

## Contrato y corrección

`return_flow.py` detecta la redeclaración block-scoped y **rechaza el callable**
con una razón explícita, en lugar de inventar la unión:

- Un declarador es `op.kind == 'ASSIGN' and op.native_kind == 'variable_declarator'`
  (mismo `native_kind` en Java, JS, TS y C#; verificado en los cuatro grammars).
- Se camina hacia arriba hasta el bloque léxico más cercano
  (`block` / `statement_block` / `compound_statement`).
- Solo cuentan los declaradores *block-scoped* del lenguaje:

  | Lenguaje | Wrapper block-scoped | `var` (function-scoped) |
  |---|---|---|
  | javascript / typescript | `lexical_declaration` (`let`/`const`) | `variable_declaration` — excluido |
  | java | `local_variable_declaration` | — |
  | csharp | `variable_declaration` | — |

- Si un mismo binding tiene declaradores block-scoped en **más de un bloque**,
  el frontend los colapsó: `RETURN_FLOW_STATUS = unsupported`,
  `reason = 'shadowed-binding'`.

El rechazo es deliberado y sigue el criterio del plan: si el modelo no puede
representar dos bindings, el resultado correcto es **unknown**, no un `may`
inventado. Es la misma política que el pase ya aplica a bucles, `try`, closures
y escrituras no locales.

## Qué NO se rompe (verificado con tests)

| Caso | Comportamiento | Motivo |
|---|---|---|
| JS/TS `var` redeclarado en `if` | `supported`, `may` con 2 orígenes | `var` es function-scoped: es **un** binding y la rama realmente cambia el valor |
| `var` redeclarado en el mismo bloque | `supported`, `must` con el último valor | mismo bloque, un binding |
| Asignación simple dentro de una rama | `supported`, `may` con 2 orígenes | una asignación no es una declaración (territorio P1.4) |
| Declaración sin valor + escritura posterior | `supported`, `unknown` antes y `must` después | orden preservado |
| Shadowing en bloque desnudo (Java/C#) | `unsupported` | ya se rechazaba; la razón puede ser `nonlocal-or-nested-write` |
| Shadowing de parámetro | `unsupported` (`nonlocal-or-nested-write`) | `locals_by_owner` vacío: el target no es un STORAGE local |
| Python | sin cambio | Python no tiene ámbito de bloque; el pase no se rechaza por esta regla |
| Python comprehension | sin cambio | el call interno del comprehension no se modela (conservador) |

## Límite real y trabajo pendiente

**Esto elimina un hecho falso, no resuelve el caso.** El pase sigue sin
distinguir los dos bindings, así que pierde toda la procedencia del callable
(igual que con otras construcciones no modeladas). La resolución correcta
requiere que el frontend emita **STORAGE distintos por declaración**.

Diseño propuesto para el frontend (no implementado):

1. **Identidad.** `Frontend.entity` arma la clave como `{scope}/STORAGE:{name}`,
   de modo que dos STORAGE con el mismo nombre y scope **colisionan**. Hay que
   añadir un sufijo de bloque a la clave (p. ej. `{scope}/STORAGE:{name}@{block.start_byte}`)
   manteniendo `Entity.name` con el spelling original para no romper a los
   consumidores que comparan por nombre.
2. **Registro.** Un mapa nuevo `self.block_locals[(scope, block_id, name)]`.
   Se puebla solo cuando la declaración es block-scoped, está en un bloque
   distinto del cuerpo y el nombre ya está ligado en el callable (shadowing).
   Sin shadowing el camino actual queda intacto byte a byte.
3. **Lecturas.** En `Frontend.value`, rama de identificadores, resolver primero
   por el bloque léxico más cercano y caer a `resolve_name` si no hay
   declaración en el bloque. El helper `enclosing(node, kinds)` ya existe.
4. **Caché.** Cambia la forma de las entidades persistidas: subir `IR_VERSION`
   (1.48.0 → 1.49.0) para invalidar cachés.
5. **Tests.** Al resolverse, el caso positivo debe dar
   `RETURN_FLOW_STATUS = supported` y `ARGUMENT_ORIGIN` con `modality='must'` y
   **un** origen (`make(1)`), no `unsupported`. La matriz de
   `tests/structural/test_scope_shadowing.py` es el oráculo.
