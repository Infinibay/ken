# P1.1 — Ámbitos y shadowing block-scoped (IR 1.49)

Estado: **shadowing block-scoped resuelto**. Quedan fuera de esta entrega las
closures y el shadowing de parámetros, que siguen siendo conservadores.
Fecha: 2026-09-13. Base: `1ee12c1` (post manifiesto de xfail).

## Problema reproducido

El frontend indexaba un binding local por `(owner, nombre)`
(`Frontend.storage` → `self.names[(scope, name)]`), así que **dos declaraciones
con el mismo spelling en bloques léxicos distintos de un mismo callable
colapsaban en un único `STORAGE`**. El pase `structured-locals/3` recorría las
ramas y unía las escrituras de ambos bindings como si fueran uno solo, emitiendo
un origen que **no es alcanzable** en el punto de lectura.

Java, dentro de una región (`if`), que es lo que hacía que el pase no lo
rechazara:

```java
class A {
  static int make(int n){ return n; }
  static int take(int n){ return n; }
  static int run(boolean flag){
    int x = make(1);
    if (flag) { int x = 0; take(x); }
    return take(x);
  }
}
```

Observado antes del cambio (idéntico en javascript, typescript y csharp):

```text
status: supported
ARGUMENT_ORIGIN CALL:188@188:195  operand=STORAGE:x
  modality=may  origins=[CALL:130@130:137, VALUE:163]
```

`CALL:130` es `make(1)` y `VALUE:163` es el literal `0` **del `x` sombreado**.
En `return take(x)` el `x` interno ya está fuera de alcance: el único origen
posible es `make(1)`. El pase fabricaba una unión imposible.

Por qué `if` y no un bloque desnudo: un bloque `{ ... }` no es región y el pase
ya lo rechazaba con `nonlocal-or-nested-write`. El brazo de un `if` **sí** es
región, así que el write sombreado entraba en el merge de brazos.

## Corrección en dos capas

### 1. Frontend: identidad por bloque léxico (arreglo principal)

- Constantes nuevas: `BLOCK_SCOPES` (`block`, `statement_block`,
  `compound_statement`) y `BLOCK_DECLARATIONS`.
- `Frontend.block_scope(node)` / `is_body_block(block)`: bloque léxico más
  cercano, distinguiendo el cuerpo del callable.
- `Frontend.block_storage(name, scope, block, node)`: cuando una declaración
  block-scoped **sombrea** un binding ya ligado en el callable, se crea una
  entidad propia con la clave `<owner>/STORAGE:nombre@<byte del bloque>` y el
  atributo `block_scope`. `Entity.name` conserva el spelling original, así que
  los consumidores que comparan por nombre no cambian.
- `Frontend.block_local(name, scope, node)`: resuelve lecturas caminando hacia
  afuera desde el nodo; gana la declaración del bloque más cercano y el binding
  interno deja de aplicar al salir de su bloque. La rama de identificadores de
  `Frontend.value` la consulta antes de `resolve_name`.
- La rama de declaración local solo usa `block_storage` cuando la declaración es
  block-scoped, está en un bloque que **no** es el cuerpo del callable y el
  nombre ya estaba ligado. Sin shadowing el camino previo queda intacto.

Alcance por lenguaje:

| Lenguaje | Declaración block-scoped | No se separa |
|---|---|---|
| javascript / typescript | `lexical_declaration` (`let`/`const`) | `var` (`variable_declaration`) es function-scoped |
| java | `local_variable_declaration` | — |
| csharp | `variable_declaration` | — |
| python | — (no tiene ámbito de bloque) | sin cambios |

`IR_VERSION` sube a **1.49.0** porque cambia la forma de las entidades
persistidas.

Resultado en el caso reproducido:

```text
DECLARES(storage):  CALLABLE:run@88 -> STORAGE:x        (name=x)
                    CALLABLE:run@88 -> STORAGE:x@153    (name=x)
ASSIGNED_FROM:      STORAGE:x      -> CALL:130@130:137  (make(1))
                    STORAGE:x@153  -> VALUE:163         (literal 0)
ARGUMENT_ORIGIN:    CALL:166 (take interno)  operand=STORAGE:x@153
                      modality=must origins=[VALUE:163]
                    CALL:188 (take del return) operand=STORAGE:x
                      modality=must origins=[CALL:130@130:137]
```

Cada lectura resuelve a su binding con **un** origen cierto: ya no hay unión.

### 2. Pase: rechazo como red de seguridad

`return_flow.py` conserva la detección agregada en la primera parte de la
entrega. Si un mismo binding tiene declaradores block-scoped en **más de un
bloque**, el frontend no logró separarlos (p. ej. una declaración anidada
procesada antes que la externa, cuando todavía no existe binding a nivel de
callable) y el pase rechaza con `reason='shadowed-binding'` en lugar de publicar
la unión inventada. La firma general del pase y sus otras razones no cambian.

## Qué NO se rompe (verificado con tests)

| Caso | Comportamiento | Motivo |
|---|---|---|
| JS/TS `var` redeclarado en `if` | `supported`, `may` con 2 orígenes | `var` es function-scoped: es **un** binding y la rama realmente cambia el valor |
| `var` redeclarado en el mismo bloque | `supported`, `must` con el último valor | mismo bloque, un binding |
| Asignación simple dentro de una rama | `supported`, `may` con 2 orígenes | una asignación no es una declaración (territorio P1.4) |
| Declaración sin valor + escritura posterior | `supported`, `unknown` antes y `must` después | orden preservado |
| Shadowing en bloque desnudo (Java/C#/JS) | `unsupported` (`nonlocal-or-nested-write`) | el bloque no es región; ahora con dos bindings separados pero sin región que recorrer |
| Shadowing de parámetro | `unsupported` (`nonlocal-or-nested-write`) | el binding interno ya es distinto, pero el bloque desnudo sigue sin ser región |
| Python | sin cambio | Python no tiene ámbito de bloque |
| Python comprehension | sin cambio | el call interno del comprehension no se modela (conservador) |
| Orden invertido (anidada antes que la externa) | `unsupported` (`shadowed-binding`) | el frontend no pudo separarlas: red de seguridad del pase |

## Límite y trabajo pendiente

- **Closures**: un callable anidado sigue rechazándose con
  `nested-or-dynamic-execution`. Distinguir captura de valor vs de binding es
  P4, no P1.1.
- **Shadowing de parámetro resuelto como binding distinto** (se crea
  `STORAGE:x@…`), pero el caso de prueba cae en un bloque desnudo y el pase lo
  rechaza igual. Con una región (`if`) el parámetro externo y el local interno
  ya se separan correctamente.
- **Orden de declaración**: si la declaración anidada se procesa antes que la
  externa, el frontend asigna el `STORAGE` de nivel callable y el pase rechaza.
  Resolverlo requiere una pasada previa que registre todas las declaraciones
  antes de resolver lecturas.
