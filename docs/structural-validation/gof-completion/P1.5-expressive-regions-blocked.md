## Síntoma reproducible

`take(x or make(2))` y `y = 2 if flag else 3` en Python (lenguaje soportado)
no producen `ARGUMENT_ORIGIN` ni `RETURN_ORIGIN` desde el pase
`src/ken/structural/return_flow.py`. El callable no se marca como
`unsupported` (sale `supported`), pero los hechos de procedencia sobre el
operando del cortocircuito no se emiten, o se emiten sólo sobre el VALUE
opaco del propio cortocircuito.

```python
def run(flag):
    x = 1
    take(x or 2)
```

Diagnóstico: `snapshot(value)` trata el `VALUE` del `boolean_operator` como
un valor opaco. Si el operando no es un `STORAGE` local, devuelve `unknown`.
El cortocircuito no se descompone en la unión de los snapshots de sus
operandos `left`/`right`.

Mismo síntoma para `BRANCH right conditional_expression` y `BRANCH right
ternary_expression` en Java/TS/JS/C#.

## Lo que el plan exige

> *"Respetar `choose`, cortocircuito, orden de argumentos soportado y
> retornos abruptos. No evaluar ambos brazos como secuencia."*

El contrato mínimo para aceptar un caso:

- `take(a or b)` con `a = make(1)` (STORAGE local) y `b = 2` (literal)
  debe producir `ARGUMENT_ORIGIN` para el `take` con `modality='may'`,
  `origins=[VALUE de make(1), literal 2]` (o al menos el VALUE del call
  cuando el literal no sea representable como origen con ID estable).
- El caso negativo: `take(a or b)` con `b = other(1)` y `a` reasignado
  a `0` antes del `take` debe seguir mostrando `must`/`may` correcto
  según IR 1.48 (no inventar `must` por ver el `BINARY`).

## Por qué no se cerró en esta sesión

1. El mapeo VALUE → BINARY/BRANCH por span funciona, pero los operandos
   del BINARY no tienen entities (`left identifier`, `right integer`):
   el identifier `x` no emite VALUE/STORAGE entity con su propio span;
   sólo apunta al STORAGE `x` por nombre. `_operand_entity` devuelve
   `None` para `left` y `right`, y la unión queda vacía → fallback
   `(value, None)` → mismo resultado que el baseline.
2. Para que la unión produzca orígenes reales, hay que caminar el árbol
   sintáctico hasta encontrar el STORAGE o CALL referenciado por cada
   operando. Eso requiere una segunda tabla de mapeo que el pase actual
   no construye.
3. El walk también debe tratar el BINARY/BRANCH como **una región con
   dos brazos** (no como dos assignments consecutivos), porque sólo uno
   se ejecuta. Sin esa región, los snapshots se mezclan en una lista y
   se pierde la información de exclusividad.

## Aceptación mínima P1.5 (texto del plan)

> *"Aceptación mínima P1: en cada lenguaje admitido, `x=make(); use(x)`
> positivo; `x=make(); x=0; use(x)` negativo; uso anterior a make
> negativo; `x=make(); saved=x; x=0; use(saved)` positivo; shadowing y
> ramas mutuamente excluyentes no se mezclan. Añadir dos argumentos
> con el mismo spelling y orígenes independientes."*

Los cuatro primeros casos ya pasan en IR 1.48. P1.5 añade:

- `x=make(); use(x or other())` positivo con `may` y unión de
  orígenes.
- `x=make(); use(x and other())` positivo con `may` y unión de
  orígenes (en JS/TS `and`/`or` devuelven el operando seleccionado,
  no booleano: modelar la diferencia con `result_policy`).
- `x = a if flag else b; use(x)` positivo con `may` y unión de
  orígenes para `x` antes del `use`.
- Negativos: RHS opaco (call no resuelto), brazo inalcanzable en
  práctica, ramas con origen único pero distinto.
